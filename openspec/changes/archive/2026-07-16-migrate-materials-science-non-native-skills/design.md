## Context

The Materials converter currently resolves a complete immutable audit and
production policy, but emits seven thin trees by copying or replacing the 24
files under admitted upstream Skill roots. The generated `SKILL.md` files are
only 22–25 lines, ordinary execution is spread across short quickstarts and
copied references, and external-tool use lacks a complete configuration,
authority, result, and recovery contract. Converter version 1 has no capability
definition, complete-tree validation, derivation file, or aggregate approval
hash.

The immutable `snapshot-fafd3ab` audit, admission decisions, MIT conclusion,
fixed IDs, memberships, relationships, external-resource classifications, and
empty hard dependencies remain authoritative. This migration changes the
runtime form and approval model, not the admitted scientific scope.

## Goals / Non-Goals

**Goals:**

- Make every published Materials Skill executable from its copied tree and
  complete main file using the lowest sufficient non-native thickness.
- Give every advertised capability one primary Agent-procedure or external-tool
  implementation and retain only substantial conditional references.
- Preserve exhaustive source coverage while replacing one-to-one replacement
  assets with explicit source-to-authored-output derivation.
- Bind production bytes to a reviewed aggregate hash and upgrade the isolated
  converter to version 2 without changing other vendor projections.

**Non-Goals:**

- Changing the immutable audit, seven/five admission split, fixed IDs, domain
  catalog, membership, licensing, relationships, or hard dependencies.
- Adding bundled computation, provider clients, installation, downloads,
  credential discovery, state, gates, generic runners or schemas, public
  commands, or ResearchSpec workflow authority.
- Formally benchmarking LLM behavior or executing scientific/HPC software as
  part of conversion, checking, packaging, or installation.

## Decisions

### Use one Tier 1 and six Tier 2 Skills

Atomsk is a complete baseline external-tool procedure without references.
APEX, DeePTB, DP-GEN, GPUMD, Phonopy, and Uni-Mol each retain exactly one
substantial reference for conditionally needed property, configuration, file,
or mode detail. Their main files already contain the governing rule and
ordinary decision path. Short quickstarts, resource lists, safety paragraphs,
and troubleshooting notes move into the main file. No Skill needs scripts or
state because all deterministic execution belongs to user-configured scientific
software and no cross-session authority is required.

### Author complete trees instead of composing replacement fragments

`skill-definitions.ts` is the typed SSOT for IDs, tiers, capabilities,
implementation mechanisms, reference routes, memberships, and empty hard
dependencies. `skills/<id>/` contains complete current-state main files and
references. `complete-tree.ts` copies reviewed authored bytes and adds only the
MIT `LICENSE`, source-bound `NOTICE.md`, and generated `DERIVATION.json`.

The 24-record file catalog remains exhaustive source evidence but changes from
renderer instructions to `adapted` or `excluded` decisions with explicit
derived output paths. The obsolete `curation_profile`, replacement asset hashes,
and `curation/**` renderer inputs are removed after the complete trees are
approved.

### Separate scientific judgment from tool execution

Agent procedures own scientific intent, parameter justification, dataset and
model applicability, convergence, uncertainty, evidence conflicts, and result
interpretation. External-tool mappings own real execution through user-managed
APEX, Atomsk, DeePTB, DP-GEN, GPUMD/NEP, Phonopy, DFT/ALM, and Uni-Mol entrypoints.
Every tool contract states configuration, authority, data boundary, expected
result, side effects, confirmation points, and unavailable-tool recovery.

### Bind complete-tree approval and switch directly to final version 2

`review-decision.json` binds the immutable audit and the exact aggregate hash of
the complete authored trees. The implementation produces a Chinese review
artifact containing per-tree and aggregate hashes, thickness, references,
capability coverage, source derivation, permissions, and tests. The user's
instruction to proceed directly to the final target authorizes promotion of the
exact generated hash in this implementation turn; any subsequent byte change
must recompute and rebind the approval before conversion succeeds.

### Keep converter and registry isolation

Version 2 stages all five published vendors but emits and commits only the
Materials tree, bundle, manifest, report, and source-neutral registry. The
manifest records the approved tree-set hash, per-tree and per-file hashes,
implementation counts, policy hashes, source dispositions, and relationships.
Other vendor projections must remain byte-identical.

## Risks / Trade-offs

- **[A reference becomes an alternate runtime controller]** → Keep one
  conditional reference per Tier 2 tree, validate direct read conditions, and
  record the context-saving rationale in the hash-bound review.
- **[An external-tool mapping remains a vague provider placeholder]** → Require
  concrete tool names, configuration and authority anchors, expected outputs,
  and recovery in both typed definitions and the main file.
- **[Source consolidation loses provenance]** → Preserve all 24 source hashes,
  require derived output paths for every adapted record, and render per-Skill
  `DERIVATION.json` from those decisions.
- **[Scientific software is accidentally executed during maintenance]** → Ship
  no scripts, installers, service adapters, or credentials and test copied trees
  structurally outside the repository.
- **[Materials regeneration changes another vendor]** → Compare all unrelated
  vendor projections during conversion and idempotence verification.

## Migration Plan

1. Add typed definitions, complete authored trees, source derivation policy,
   complete-tree rendering, review state, and focused validation.
2. Render the candidate trees, compute all hashes, write the Chinese review
   artifact, and bind the exact aggregate hash as approved under the user's
   direct-final-target authorization.
3. Select converter version 2, remove obsolete curation assets and renderer
   branches, regenerate Materials assets and the combined registry, and update
   release/documentation contracts.
4. Run strict OpenSpec validation, focused and full tests, checks, build, all
   vendor isolation/idempotence commands, release verification, and whitespace
   validation.

Before version 2 generation, rollback removes the new authored inputs and
review state. After promotion, rollback requires restoring the prior generated
tree and converter together; an old approval cannot authorize different bytes.
