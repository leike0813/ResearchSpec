## Context

The adaptive runtime already exposes plan-bound actions, Case obligations, formal Gates, Decisions, receipts, and Doctor diagnostics, but authority rules are repeated across command handlers and transaction types. Receipts record too little information to distinguish an exact retry from a new action after a partial write. Main specs and generated guidance also contain overlapping requirements from successive runtime refactors, while several tests validate prose and source layout instead of stable behavior.

The implementation must preserve the adaptive default, Schema `0.2` strict compatibility, fixed public command and Skill surfaces, file-based authority, and human confirmation at every formal Gate.

## Goals / Non-Goals

**Goals:**

- Derive every action's execution contract from `execution_policy` and enforce it through one guard.
- Give all adaptive Gate operations one authority resolver and one definition of current evidence, readiness, override validity, and completion.
- Make adaptive transactions exactly retryable from receipt v2 after bounded write interruption.
- Make Doctor and static checks compare receipts and authority in both directions.
- Restore CLI portability and contextual help correctness without dependencies or public-surface changes.
- Make canonical requirements and durable behavioral tests the maintained sources of truth.

**Non-Goals:**

- No new command, Skill, wrapper, tool registration, runtime mode, dependency, or LLM integration.
- No automatic receipt v1 migration or inferred reconstruction of missing semantics.
- No redesign of strict compatibility transactions, Zotero admission, vendor review decisions, or approved generated bytes beyond converter-owned guidance updates.
- No rewrite of archived OpenSpec change history.

## Decisions

### Execution policy owns the executable contract

ActionDescriptor v2 will expose `execution_requirements` derived from the selected `execution_policy`. A shared guard will preview the exact bound plan and hash. Interactive execution requires confirmation after preview; non-interactive execution requires a matching action basis, plan hash, and `--yes`. Gate, Decision, and patch application will call the same guard.

Keeping per-handler checks was rejected because small differences already allow authority-changing actions to bypass the intended contract. A constant `dry_run` hint was rejected because it describes no policy-specific requirement.

### Gate authority is resolved from typed current evidence

A shared resolver will select the latest trustworthy event for one Gate, recognize both `pass` and `pass_with_conditions` as satisfying verdicts, and reject cross-Gate, stale, or fabricated reverification links. A failed reverification creates a pending override case action. Only an accepted Decision bound to the latest Gate event and receipt can activate it; any newer Gate event invalidates the old action.

Waiver and not-applicable Decisions can satisfy obligation readiness, but a formal Gate still requires a user-confirmed Verify verdict. Gate evidence stores typed Decision references with Decision/event identity and receipt path, hash, and plan hash.

### Receipt v2 is a replay certificate

New adaptive receipts will include action identity, normalized semantic input, complete read preconditions, and the authority target/projection, in addition to effects and plan hash. Transaction planners will use the same normalized input for initial execution and exact retry.

A retry reconciler will inspect completed phases and write only missing deterministic phases. Existing event IDs and semantic projections make ledger append idempotent; contradictory projections or changed preconditions are conflicts. Receipt v1 remains schema-readable, but any recovery that requires absent semantics is classified `requires_human_reconstruction`.

### Doctor and check share integrity resolution

One integrity resolver will power receipt-to-authority and authority-to-receipt/state checks. Doctor may plan only a unique deterministic repair or exact transaction retry. Static check reports the same inconsistencies without executing repair.

### Canonical behavior replaces prose scanning

Main specs will contain one current requirement for each runtime/public-surface behavior. Tests will exercise public DTOs and observable transitions with table-driven or unordered assertions. Release verification will retain package topology, schema, hash, link closure, license, safety, and public-interface checks while dropping natural-language tokens, diagram semantics, Markdown IDs, and source-code regex assertions.

### Build permission is a Node operation

The package build will call a small Node script or inline Node file-API operation to set executable bits. This works on the existing Node 22/24 matrix and avoids adding a dependency or inspecting shell script text in tests.

## Risks / Trade-offs

- [Receipt v2 expands durable metadata and schema code] → Keep one normalized transaction envelope and a read-only v1 union branch.
- [A shared Gate resolver can expose previously tolerated inconsistent ledgers] → Return typed stale/cross-Gate/conflict diagnostics and require a new verified event rather than silently accepting history.
- [Retry reconciliation touches multiple write phases] → Use stable event IDs, precondition hashes, post-write validation, and fault-injection tests for every adaptive action family.
- [Removing brittle tests reduces superficial coverage] → Retain stable product counts, schemas, hashes, approved bytes, drift/idempotence, licensing, safety exclusions, and public behavior tests.
- [Generated guidance can drift from authored sources] → Regenerate only through the converter and run handbook, converter, release, and idempotence checks.

## Migration Plan

New writes immediately use receipt v2. Readers accept v1 and v2. No existing receipt is rewritten. Doctor reports v1 transactions that cannot be proven as `requires_human_reconstruction`; operators can resolve them through an explicit human-reviewed recovery. Rollback consists of reverting code and generated artifacts; receipt v2 remains non-destructively present and must be treated as an unknown newer schema by an older release.

## Open Questions

None. The accepted plan fixes the product boundaries and legacy receipt policy.
